## Recommendation

Use **Event Timing for eligible native dispatch timestamps**, plus **one short CDP trace for the actual game operation**, joined to an independently validated retained visual cue. Add only before/after native counters if they answer a remaining work question. Event Timing cannot cover gesture motion; trace activity alone cannot identify the game's meaningful response. Neither replaces the full functional oracles or the separate first-feedback/completion records.

### 1. What Event Timing measures

The following are the current W3C draft contract, not a promise that every field ships in this browser:

| Field | Meaning |
| --- | --- |
| `startTime` | Associated DOM event's `timeStamp`. |
| `processingStart` | Beginning of dispatch, before handlers. |
| `processingEnd` | End of dispatch; not completion of asynchronous work caused by it. |
| `duration` | Input timestamp to subsequent rendering update; rounded to nearest8ms. |
| `name` / `entryType` | DOM event type / `event` or `first-input`. There is no public `entry.event` carrying the original Event. |
| `interactionId` | Groups related tap/drag or key events; not a pointer ID or operation counter. Noninteraction events can have0; a scrolling pointerdown is excluded from an interaction. |

Owning definition and algorithms: [Event Timing §§2.1,3.1,3.6–3.9][et]. **Inference:** the next rendering update can precede asynchronous useful results or paint unrelated animation; it does not identify action-related camera/panel/playhead/loading/save/art changes.

`pointerdown`, `pointerup`, `click` are eligible, subject to trust/filtering/reporting; `pointermove`, `pointerrawupdate`, `touchmove`, `mousemove`, `wheel` are excluded. Chromium147's actual filter confirms this and captures native processing times independently of JS listeners. Browser-driven input must demonstrate eligibility; `dispatchEvent()` is no substitute. [147 `event_timing.cc`, `IsStandardEventType`, constructor/destructor][et-hook]; [DOM trust definition][dom].

Use `observe({type:'event', durationThreshold:16, buffered:true})` **before input**. Default threshold104ms; minimum16ms. Chromium147 clamps the requested threshold to16 and compares against the entry duration: do not assert that the threshold argument itself is rounded to8. `takeRecords()` drains already queued observer entries; `disconnect()` clears that observer's pending buffer. Drain before disconnect, after a bounded reporting grace. Neither forces an unfinished entry to finalize. [147 observer implementation][po-src], [default constant][po-header].

Chromium147 rounds duration to8ms, buffers historical events only at the default104ms cutoff, and can wait for presentation and interaction-ID resolution. Pointer creation uses the **oldest coalesced platform timestamp**, whereas ordinary events use their platform timestamp. It has no-next-paint, visibility, broken-presentation and other fallback paths; hidden/detached lifecycle cases can flush or clear pending entries. Entries need not have event listeners, and targets can be retargeted or detached before delivery. [147 `window_performance.cc`, processing/flush/report paths][window]. The entry implementation chooses fallback over presentation when present; public `toJSON()` does not expose a fallback-reason field. `target` is nullable and subject to node-exposure rules; do not require experimental `targetSelector`. Its legacy trace arguments include unrounded duration, frame/node identity and origin-relative millisecond timing fields; these are version-specific diagnostics. [147 entry implementation][entry-src].

Handler timestamps have `performance.now()`-class precision, **not duration's8ms precision**. HR-Time uses monotonic origin-relative milliseconds; coarsening can be100µs or coarser normally,5µs or coarser with cross-origin isolation, with implementation-defined jitter. Validate actual resolution/isolation; decimal digits are not accuracy evidence. [Event Timing privacy section][et]; [HR-Time §§2–5][hr]. Treat `startTime+duration-processingEnd` as approximate, potentially negative from rounding; retain the raw value before any separately labelled display clamp.

Lifecycle/accounting: Performance Timeline delivery is asynchronous; its buffer is bounded, `buffered` recovers only retained history, and optional callback `droppedEntriesCount` concerns timeline buffer loss, not every missing input. Supported types and dropped-count availability must be recorded; unsupported/absent is not zero. [Current Performance Timeline draft §§2,4,5][pt]. Event Timing's first-input entry bypasses duration filtering but is only the first interaction, not a per-job fallback; pointerdown may wait for up/cancel to resolve grouping. [Event Timing §§1.3,3.6–3.9][et].

**No entry does not mean zero latency, or even a proved <16ms sample.** Account separately for: excluded type, ineligible/untrusted input, below-threshold possibility, pre-observer history cutoff, pending grouping/paint, navigation/visibility/destruction, native loss, observer export overflow, ambiguous match and unexplained missing entry. Thresholded entries are a selected population: do not compute a whole-job P50/P95 from them.

### 2. Native queue delay and original-event matching

**Yes, conditionally:** native `processingStart` precedes HC/pre-handler JS reads and can corroborate their arrival timing independently. Chromium147 creates UIEventTiming before capture/bubble handling; its `EventDispatch` trace slice starts later in that function. They are distinct native boundaries, not numerically interchangeable. [147 dispatcher][dispatch]. “Independent” means timestamp acquisition, not an uninstrumented workload: JS readers can still lengthen processing, later queues and rendering.

Required diagnostic proof, on the real input path:

1. Preserve exact original HC `started`, `handlerStarted`, `inputQueueMs`, plus window pre-read arrival, read start/end, feedback arrival and event metadata. Never replace HC's original queue field or subtract a reader's cost and rename the remainder product queue.
2. Match by document/navigation generation, operation window, event type, target/canvas identity, timestamp tolerance, and ordered trusted receipt ledger. Keep pointer identity, coordinates/buttons and coalesced timestamps in that ledger. Public Event Timing has no pointer-ID/coordinate/original-event fields; an interaction ID can cover several events. Canvas target identity alone is insufficient. Reject multi-match; don't select “nearest” without a proved unique join.
3. Prove the start timestamps refer to the same input. DOM `event.timeStamp` in147 converts the event's platform timestamp relative to the current realm; PointerEvent's oldest timestamp may instead be the first coalesced timestamp. [147 Event getter][event-src]; [147 PointerEvent implementation][pointer-src]. Retain both. An unexplained discrepancy blocks subtraction/comparison; no forced equality or tolerance widened after results.
4. For a matched common start `I`, retain native queue `processingStart-I`, HC arrival `handlerStarted-I`, and their difference `handlerStarted-processingStart` as **pre-HC dispatch/observer interval**. Feedback arrival minus HC arrival also contains intervening work, not just the captured reader. Quantization tolerances apply; negative/out-of-order values are flagged, not repaired.
5. Run separate known pre-dispatch-queue and known capture-reader-cost controls. The former must move native queue; the latter, placed after native processing start, must move the downstream interval/processing cost without being relabelled original queue. Prove window-capture → HC → app-handler ordering with actual trusted input. Do not infer it from a JS-dispatched model, listener names, or a microtask receipt.

Clock rules: keep raw origins/units. Same-document Event Timing, DOM events and `performance.now()` are comparable only after the above source/realm checks. Translate worker-relative timestamps using both `timeOrigin`s, never equal raw worker/main `now()` values. [HR-Time cross-context example][hr]. CDP Input's optional timestamp is **UTC seconds**, not page milliseconds or Chromium monotonic ticks; host scheduled time, protocol acknowledgement and browser event timestamp are three different observations. [147 Input protocol][input]. Native queue is input-timestamp-to-dispatch delay, not necessarily pure renderer-queue residence; synthetic protocol input does not establish physical hardware arrival.

### 3. Small CDP protocol and evidence boundaries

Future capability check: retain `Browser.getVersion` (product/revision/protocol version), actual launch flags, served build/harness/oracle/fixture identities, renderer configuration and context lifecycle. `getVersion` has those version fields; protocol version alone does not pin implementation. [147 Browser protocol][browser]. Current CDP master and matching147 PDL were read; use the latter below. All runtime support remains untested.

**Proposed trace lifecycle**, one owner/session, no simultaneous DevTools/Playwright trace:

1. Register completion/error handlers before start. Discover categories once with experimental `Tracing.getCategories`; freeze the returned category selection. Start with `devtools.timeline`, `blink.user_timing`, `disabled-by-default-devtools.timeline.inputs`, plus `cc` for compositor evidence, only as actually available. If the minimum chain is absent, allow one separate discovery capture adding the source-justified missing category, then report unavailable rather than expanding indefinitely.
2. `Tracing.start({transferMode:'ReturnAsStream', streamFormat:'json', traceConfig:{includedCategories:[...frozen categories...]}})`; omit deprecated `categories/options`. No stack sampling, screenshots, memory dumps or system tracing. Run exactly the ordinary job and its declared settling window. Default stream format is JSON, compression none. Category discovery, clock-sync marker, sampling/buffer controls and format types have experimental parts; JSON is marked for future deprecation. [147 Tracing PDL][tracing].
3. Call `Tracing.end()` once; its response is not completed delivery. Await `Tracing.tracingComplete`, retain `dataLossOccurred`, stream handle and actual format/compression. Reject missing flush, loss or incomplete required slices as corroboration gaps. A false loss flag alone cannot establish producer/category coverage. The147 handler sends stream metadata only after stream completion. [147 tracing handler][trace-handler].
4. Sequential `IO.read({handle,size:65536})` to `eof`, decode each `base64Encoded` chunk when flagged, preserve chunk order, enforce a proposed64MiB total/15s drain cap; parse the complete stream. `IO.close({handle})` in `finally` releases temporary backing storage. Do not interpret arbitrary chunks as complete JSON. [147 IO protocol][io].
5. Proposed cancellation policy: operation failure/timeout still requests end if this session started; retain partial/error status, drain if possible, close any delivered handle, remove listeners and disconnect diagnostic observers. Use15s stop/flush deadline. Start failure must not end someone else's trace. If session/browser dies, or stop cannot complete, mark trace/cleanup incomplete and discard the dedicated diagnostic context/process before another run. There is no separate trace-cancel command in this protocol; end is the normal stop. [147 Tracing command set][tracing]. No “cancel means successful trace” shortcut.

Proposed capture cap:60s per normal job, including its unchanged completion timeout/settle policy; if the declared job needs longer, predeclare that exception before collection. Reaching the cap yields a truncated diagnostic, not permission to shorten opening/reveal or to report a faster job. Freeze byte/time caps before execution.

**Joining evidence, without inventing stable names:**

- In147, `EventDispatch` is emitted under `devtools.timeline`, before capture/bubble handlers. Its arguments always contain event type; the disabled inputs category adds source timestamp (monotonic **microseconds since origin**) and mouse coordinates/buttons. It does not promise a public Event Timing interaction-ID join. [147 dispatch emitter][dispatch]; [147 argument writer][trace-args]. Prove mapping on one event before interpreting a whole gesture.
- Emit diagnostic-only marks with unique document/operation/receipt IDs at capture, first retained cue detection and frame-opportunity validation; retain raw JS timestamps and baseline/source identity. `performance.mark()` supplies page-relative marks, not native presentation witnesses. [User Timing §3.1.1][ut]. First confirm these marks appear under the selected trace category. No mark is an exact mutation timestamp unless emitted at a separately proved application boundary; a sampled cue gives a detection bound.
- Look for renderer work and a compositor submission/presentation chain for the **same surface/frame lineage**, not merely a nearby paint.147 compositor source has `PipelineReporter` with frame source/sequence, layer-tree identity and presented/partial/dropped/no-update states under `cc` and related categories. This is a source-supported discovery candidate, not a stable CDP trace schema; legacy JSON may omit typed details. [147 compositor reporter][compositor]. Freeze only names/fields actually observed and source-checked. Missing surface joins remain unavailable. Add `viz` only in the bounded discovery follow-up if needed; do not invent a universal `FramePresented` counter.
- There is no generic native CDP field meaning “the game's camera/panel/playhead was correctly applied.” Join a validated retained cue, then independently inspect content in a separate bounded visual diagnostic: before/after PNGs for persistent cues, or a short source-verified filmstrip for transient phases. `Page.captureScreenshot` returns image data, with PNG default; surface selection is experimental. [147 Page protocol][page]. Screenshots verify captured content, not the exact first visible instant. For a filmstrip,147's screenshot handler explicitly labels expected display time an **estimate**; don't promote it to measured scanout. [147 screenshot handler][trace-handler].

**Units/synchronization:** Chrome JSON `ts` is microseconds; keep pid/tid/phase/flow identity and pair begin/end correctly. [Perfetto Chrome JSON documentation][json]. Convert units explicitly; do not multiply every `args.*` field by the same factor.147 legacy Event Timing trace arguments use page-origin milliseconds, while EventDispatch's input argument uses absolute monotonic microseconds. [Entry trace serialization][entry-src]; [dispatch argument writer][trace-args].

Proposed clock validation: emit5 unique immediate marks before and5 after the diagnostic window, bracketing each mark with JS `performance.now()` reads. Derive trace-to-page offset bounds from those brackets; require common offset/slope consistency and retained residuals/uncertainty. Recalibrate on navigation/context replacement. Reject joins if uncertainty exceeds HARNESS's min(5ms,input interval/4) criterion. Host/browser alignment additionally needs bounded send/receive calibration; a protocol acknowledgement is only a bracket, not event dispatch. Optional `Tracing.recordClockSyncMarker({syncId})` records a receiver marker and returns no clock conversion; it cannot alone align host and page clocks. [147 marker implementation][trace-handler]. Do not equate `timeOrigin` (epoch-relative) directly with raw trace monotonic `ts`.

**What each endpoint can establish:** HTML rAF runs before later rendering steps; two callbacks show rendering opportunities, not physical presentation. [HTML rendering algorithm][html]. DOM layout/paint, canvas rendering, rasterization, compositor work and Viz aggregation are distinct pipeline stages. A WebGL/PIXI camera change need not create a new DOM layout. [Chrome RenderingNG architecture][rendering]. JS applied state/draw commands establish CPU-side intent; submitted compositor work establishes submission; next-paint timing establishes its documented rendering endpoint; none by itself proves meaningful pixels, completed GPU execution or physical scanout. Chromium's presentation feedback distinguishes hardware-clock/hardware-completion flags from estimated timing. [147 presentation feedback contract][presentation]. This minimum protocol supplies no guaranteed GPU fence, RTX GPU duration or physical scanout evidence, especially under SwiftShader.

**Optional counters, not an alternative endpoint:** `Performance.enable({timeDomain:'timeTicks'})` → before/after `getMetrics()` → `Performance.disable()` in cleanup. The protocol returns name/value pairs, not a fixed semantic counter catalogue; deprecated `setTimeDomain` is unnecessary. [147 Performance PDL][perf].147 source emits `TaskDuration`, `ScriptDuration`, `LayoutDuration`, `RecalcStyleDuration` in seconds, layout/style counts, and JS-heap bytes. Collection attaches instrumentation; values include diagnostic work and broad renderer scope, not isolated game/GPU/worker or end-to-end response time. Capture available names once, retain raw endpoints and reset/navigation identity, and delta only appropriate cumulative metrics. JS heap is a gauge, not total process/GPU memory; no-layout delta does not disprove canvas work. [147 performance agent][perf-agent]. Keep these two calls outside the operation clock; their encompassing interval is labelled wider than the transaction. Skip them when the trace already answers the question.
