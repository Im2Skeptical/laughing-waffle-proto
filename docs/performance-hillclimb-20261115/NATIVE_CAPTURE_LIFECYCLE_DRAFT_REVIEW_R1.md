The structure has useful boundaries: job remains valid until query-zero proof; pipe reads occur on a dedicated background thread; cancellation retains that actual reader's duplicated thread handle; retained bytes/overflow remain explicit; live-stream disposal is avoided on the debug thread. README correctly says controller/drain/rollback/EOF proof is absent. Three concrete issues must be addressed before these helpers can enter a child-admitted controller.

1. **Lease native handles across their complete use.** Job calls, inheritable writer exposure and reader cancellation use DangerousGetHandle without a SafeHandle call lease. In Finish, an IsClosed check and raw handle extraction can race a concurrent Dispose after the reader stops; analogous ownership gaps exist around job disposal and writer use across creation. Return scoped leases or use SafeHandle PInvoke parameters/explicit DangerousAddRef–DangerousRelease in try/finally, with documented owner synchronization. A raw IntPtr property cannot preserve lifetime across an unknown caller's CreateProcess call. Microsoft warns returned handles can be stale/recycled; checking IsClosed is not a lease. [DangerousGetHandle](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.safehandle.dangerousgethandle?view=netframework-4.8.1).
2. **Make one real cleanup deadline govern all waits.** TerminateAndConfirm's Stopwatch does not bound a blocking Func<bool> callback; README acknowledges this. The next source must provide a finite, same-creator-thread drain implementation with explicit remaining budget and bounded event count/waits; do not offload it to an arbitrary worker thread to manufacture a timeout. Finish(waitMs) currently adds a separate500ms cancellation join after the supplied budget, and job/two-pipe waits can accumulate beyond one declared cleanup cap. Use an absolute monotonic deadline shared by job drain, pipe joins/cancellation and final proof, retaining which operation exhausted it. CancelSynchronousIo only requests cancellation and does not wait for completion, so its boolean cannot substitute for the bounded reader join/EOF result. [CancelSynchronousIo](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelsynchronousio).
3. **Complete the reader failure/disposal state machine.** Dispose sets disposed=true while a reader may still be alive, leaves its thread/event resources intentionally open, and later Dispose cannot finalize them after the reader stops. StartReader timeout/initialization failure therefore needs explicit rollback/deferred-finalization ownership; relying on eventual GC or unproved outer-host exit is not confirmed cleanup. ReadLoop's finally calls ready.Set/stream.Dispose outside the preceding catch, so cleanup exceptions can escape that background thread instead of becoming retained reader failure. Contain those terminal exceptions, safely publish stopped/error state, and permit a bounded owner finalization after confirmed join. Continue to avoid synchronously disposing a live blocked stream on the debug-loop thread. If the outer host is the final failsafe, require an actual terminated-host/job/reader proof and INCOMPLETE result rather than assuming it.

Cancellation may also race normal completion or find no pending I/O; keep its native result and final reader outcome distinct. Current conservative Error retention is fail-closed, not evidence of a native target fault. Any unconfirmed reader/handle state, raw overflow, observer error or deadline exhaustion must outrank a captured target exception in the future classifier.
