# Focused native 2D runtime options

Assessment date: **2026-11-13**. Official documentation/source review; no builds, device measurements, or FPS claims.

**Decision update:** Cam selected the custom **C++ + SDL3 + RmlUi** route.
Start implementation from [native/README.md](../../native/README.md); the shortlist
below records the research leading to that decision, not an unresolved engine choice.

Follow-up evidence: [Axmol maintenance and developer experience](axmol-maintenance-experience.md)
and [recent custom-runtime accounts](custom-runtime-developer-experience.md)
separate active support, firsthand workflow reports and actual release status.

**Recommendation:** shortlist **Axmol stable 2.x** as the focused-engine route and **C++ SDL3 + RmlUi** as the narrow-runtime route. This is engineering judgment: the workload does not require a general editor, physics system, or 3D engine. AI-assisted implementation makes a bounded custom runtime economically credible; Unity should not win by default merely because custom code once cost more.

Treat existing JS/Pixi implementation as replaceable. Retain the art and observable interaction target: an illustrated, textured procedural polygon map with roads, borders, clouds and water layers; painted cards with changing numbers/glyphs; long-text inspectors, staging and shops; life graph and custom timegraph for world inspection/scrubbing. A useful Rust/WASM experiment does not constrain the native release architecture.

| Candidate | Practical fit and objections |
| --- | --- |
| **Axmol stable C++** | Existing 2D engine, rather than components requiring an engine to be assembled. Its [2.11.5 source overview](https://raw.githubusercontent.com/axmolengine/axmol/v2.11.5/README.md) documents Windows/Android, C++, FairyGUI, audio and platform build support. Stable rendering uses OpenGL/ANGLE on Windows and GLES on Android. Sprite, polygon, label and clipping facilities reduce initial infrastructure work. Do not attribute the homepage's **v3 beta** Dynamic RHI/Vulkan/D3D12 claims to stable 2.x. Objection: custom map composition and this text-heavy UI still need work; rich text/IME and Android resource restoration need actual validation. Adopt the engine without adopting its optional physics or an editor-centric workflow. |
| **C++ SDL3 + RmlUi** | Best narrow-runtime candidate. SDL supplies platform/input/audio services; its [2D renderer](https://wiki.libsdl.org/SDL3/CategoryRender) handles textures, polygons and blending. [RmlUi](https://github.com/mikke89/RmlUi#integrating-rmlui) is a C++ UI/layout library using HTML/CSS-like documents, without embedding a browser. Its SDL platform integration includes touch/IME; renderer/platform integration remains application work, not a turnkey engine. The documented SDL GPU renderer lacks clip masks, filters and shader decorators, so prove the required clipping/effects or choose another renderer. Do not assume a desktop GL sample is an Android GLES solution. Separately, [SDL's GPU FAQ](https://wiki.libsdl.org/SDL3/FAQDevelopment#can-sdl_gpu-run-on-android) warns that Android compatibility requires relaxing Vulkan feature requirements; SDL platform support does not guarantee SDL_GPU compatibility. Test the Pixel 6's actual driver. |
| **Rust Macroquad/miniquad** | [Macroquad](https://github.com/not-fl3/macroquad#features) supplies simple batched 2D drawing, immediate UI and real Windows/Android targets; miniquad supplies its lower-level platform/graphics foundation. Credible smaller Rust alternative. Objection: included UI is not evidence that long formatted inspectors, font fallback/shaping, mobile editing, gestures and suspend/resume meet this game's needs. Prove those before selecting it for the whole interface. |
| **Rust wgpu + winit + text/layout libraries** | [wgpu](https://wgpu.rs/) is native portable graphics, despite its WebGPU-derived API; [winit's Android integration](https://docs.rs/winit/0.30.13/winit/platform/android/) provides activity/lifecycle glue. Add text shaping/rasterization and layout libraries, such as cosmic-text and Taffy. These are foundations, not a complete 2D engine: batching, atlases, clipping, hit testing, UI integration and surface/resource recovery still require assembly. Prefer only if Rust and explicit rendering control justify that ownership. |
| **raylib** | [C99 library with Windows/Android support](https://github.com/raysan5/raylib#features), usable from C++. Useful compact drawing/audio baseline, but this application's text and UI composition remain the main integration objection. |
| **Bevy** | [Rust engine with 2D, UI and Android support](https://bevy.org/), organized around ECS. Useful if its assets/tooling justify that architecture; a general ECS is optional for this deterministic domain model, not a prerequisite. |

Engine implementation language and gameplay language are separate choices. [Defold's FAQ](https://defold.com/faq/faq/#programming-language-questions), for example, distinguishes Lua gameplay from C++ native extensions; a native engine does not automatically mean writing the game in C++.

**Ownership boundary:** reuse libraries for OS integration, input, audio, font shaping, triangulation and GPU backends. Own domain simulation, timegraph and UI composition. Runtime control permits explicit allocation, cache lifetime, draw batching and forecast scheduling, but cannot remove forecast computation. Budget hidden work: font fallback/IME, nested clipping, GPU resource lifetime, Android suspend/context restoration, texture compression/atlas/shader build pipelines, hot reload, diagnostics and device debugging. AI can reduce first implementation effort; it does not establish driver compatibility, correctness or maintenance cost.

**Decision gate:** compare representative Windows and Pixel 6 release slices containing the full map/layers, card/shop/long-text interaction and scrubbing during a full opening forecast. Measure frame-time tails, input latency, forecast completion, memory and thermal behavior; exercise background/resume and resource recreation. Preserve authoritative 60-tick/s simulation, every-second summaries/loss checks, JSON-serializable state, seeded independent RNG streams, authoritative replay and independent mutable previews. Cross-platform seeded replay/serialization fixtures must agree; pin arithmetic and iteration order. This research changes no behavior, state, RNG, schemas or replay. Choose Axmol when its integrated facilities satisfy the slice; choose SDL3/RmlUi when demonstrated control benefits justify its integration burden.
